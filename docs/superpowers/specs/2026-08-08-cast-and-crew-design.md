# Cast & Crew Metadata Design

**Date:** 2026-08-08
**Status:** Draft for review
**Scope:** People storage, TMDb credits ingest, `BaseItemDto.People`, person images, `/Persons` browsing, TV credits

## 1. Summary

Hivefin stores no people. `BaseItemDto` emits no `People` array, so Jellyfin
clients show an empty cast section on every item. This adds cast and crew as
first-class, deduplicated entities: fetched from TMDb, attached to items,
rendered on item pages with headshots, and browsable so clicking an actor lists
everything they appear in.

**Delivered**

| Capability | Mechanism |
|-----------|-----------|
| Cast/crew on item pages | `people` + `item_people`, `BaseItemDto.People[]` |
| Deduplicated people | Keyed on TMDb person id |
| Headshots | TMDb `profile_path` through the existing image cache |
| Browsable people | `GET /Persons`, `GET /Persons/{name}`, `Items?personIds=` |
| TV credits | Series cast, episode guest stars |

**Non-goals**

- Person metadata beyond name, image, and role (no biography, birthplace, or
  external ids beyond TMDb — clients render these, we simply have no source
  configured for them and no request for them)
- Editing or merging people by hand
- Non-TMDb providers
- Music/audio person kinds (`AlbumArtist`, `Composer` for tracks, etc.) —
  hivefin is movies and TV only

## 2. Current state

- `Hivefin.Metadata.TMDb` fetches `/movie/{id}` with `ProviderCache`,
  `RateLimiter`, and a `Queue`/`Worker` pipeline already in place.
- `Metadata.Worker.apply_match/2` writes `overview`, `production_year`,
  `premiere_date`, and `provider_ids` onto an `Item`, and handles
  `%Item{type: :movie}` only.
- `Item` has `has_many :images`; `Image` `belongs_to :item`.
- `Metadata.ImageCache.store/3` is keyed by **item id**
  (`store(item_id, type, url)`), as is `path_for/2` and `image_tags_for/1`.
- `Dto.BaseItem` emits `ImageTags` and `PrimaryImageTag` but no `People`.
- The scanner **does** support TV (`SeriesMatcher`,
  `LibraryContext.find_or_create_series/season/episode`) and `Library.type`
  accepts `:tv`.

**Data reality:** the production library holds 7,278 movies and zero TV items,
because only a Movies library is configured. TV credits (Stage 4) are therefore
buildable but not verifiable end to end until a TV library exists. This is
called out again in §7.

## 3. Storage

Two new tables.

**`people`**

| Column | Type | Notes |
|--------|------|-------|
| `id` | `binary_id` | autogenerated, matches `Item`'s convention |
| `name` | `string` | required |
| `sort_name` | `string` | downcased name, for ordering |
| `provider_ids` | `map` | `%{"Tmdb" => "1234"}` |

Unique index on `(provider_ids->>'Tmdb')` for dedup, plus an index on
`sort_name` for `/Persons` listing.

**`item_people`** — the join carrying the per-appearance facts.

| Column | Type | Notes |
|--------|------|-------|
| `item_id` | `binary_id` | FK, `on_delete: :delete_all` |
| `person_id` | `binary_id` | FK, `on_delete: :delete_all` |
| `role` | `string` | character name for cast; nil for crew |
| `type` | `string` | `PersonKind` value — `Actor`, `Director`, … |
| `sort_order` | `integer` | TMDb `order` for cast; crew appended after |

Unique index on `(item_id, person_id, type, role)`. The same person can appear
twice on one item under different types (director *and* writer is common), so
`type` must be part of the key.

**Why not the alternatives.** A denormalised JSON column on `Item` is simpler
but makes dedup and person browsing impossible, which is most of the ask.
Modelling people as rows in `items` with `type: :person` is Jellyfin's own
design and would give images and `/Items` filtering for free — but every
existing item query would then need to exclude persons, which is a broad
regression risk across code that currently works.

## 4. Ingest

TMDb returns credits on the details call we already make, via
`append_to_response=credits`. Stage 1 therefore adds **no new HTTP request** —
only a wider response and a mapping step. The response shape:

```json
"credits": {
  "cast": [{"id": 1, "name": "…", "character": "…", "order": 0, "profile_path": "/x.jpg"}],
  "crew": [{"id": 2, "name": "…", "job": "Director", "department": "Directing", "profile_path": "/y.jpg"}]
}
```

**Mapping.** Cast → `type: "Actor"`, `role` from `character`, `sort_order` from
`order`. Crew → `type` from `job` via an explicit allowlist:

| TMDb `job` | `PersonKind` |
|---|---|
| `Director` | `Director` |
| `Writer`, `Screenplay`, `Story` | `Writer` |
| `Producer`, `Executive Producer` | `Producer` |
| `Original Music Composer` | `Composer` |

**Everything else is dropped.** TMDb returns 100+ crew rows per film (grips,
runners, casting assistants) and Jellyfin clients surface none of them. Storing
all of them would multiply the join table by an order of magnitude for data no
client displays. Unknown `job` values are dropped rather than mapped to
`Unknown`, so the table only ever holds rows a client will render.

Cast is **not** capped — clients paginate it and the row count is bounded in
practice.

Re-running metadata for an item replaces its `item_people` rows wholesale
inside a transaction. Partial updates would leave stale credits behind when a
TMDb record is corrected.

## 5. Emission

`Dto.BaseItem` gains `People[]`, each entry:

```json
{"Id": "<person uuid>", "Name": "…", "Role": "…", "Type": "Actor", "PrimaryImageTag": "…"}
```

`BaseItemPerson` declares only `Id` as required (no default in
jellyfin-sdk-kotlin); `Name`, `Role`, `Type`, `PrimaryImageTag` and
`ImageBlurHashes` are optional. **We emit `Id`, `Name`, `Role` and `Type`
unconditionally anyway.** Three separate bugs on 2026-08-07 came from trusting
that distinction: jellyfin-web dereferences optional fields (`PlayState.IsPaused`,
`AdditionalUsers.length`) with no guard, and "optional per the SDK" is not the
same contract as "safe to omit for a JS client". `Role` is `""` rather than
`null` for crew, since a client may call `.length` or `.trim` on it.

`People` is included **only** when the caller asks for it via `Fields=People`
— `include_field?(fields, "People")` and nothing else.

This deliberately differs from how `MediaSources` is gated. That one is
`playable? or include_field?(fields, "MediaSources")`, so it rides along on
every playable item whether or not the client asked. Copying that pattern would
put a full cast list on all 7,278 movies in a library listing. `People` gets the
`Fields` check alone; clients that want cast ask for it, and jellyfin-web does
on the item page.

## 6. Person images

`ImageCache` is keyed by item id throughout (`store/3`, `path_for/2`,
`image_tags_for/1`), and `Image` `belongs_to :item`. Two options:

1. Add a nullable `person_id` to `images` with a check constraint that exactly
   one of `item_id` / `person_id` is set.
2. A separate `person_images` table.

**Option 1**, because `image_tags_for/1` and the cache-path logic then work for
both with a single generalisation, and there is one place on disk where images
live. The check constraint keeps the "exactly one owner" invariant in the
database rather than in application code.

Jellyfin serves person images from `/Items/{personId}/Images/Primary` — persons
are items in its model. Our `ImagesController` must therefore resolve a
`:item_id` path segment against **items first, then people**. That is the one
place the two models have to reconcile, and it is deliberate: it keeps client
URLs identical to upstream without making people items.

## 7. Stages

Each stage is independently shippable and testable.

**Stage 1 — People on items.** Migrations, `Person`/`ItemPerson` schemas,
credits mapping, worker storing people, `People[]` on `BaseItemDto` behind
`Fields=People`.

*Done when:* a movie page in jellyfin-web lists cast with character names and
crew with roles.

**Stage 2 — Headshots.** `images.person_id`, generalised `ImageCache`,
`ImagesController` person fallback, `PrimaryImageTag` on each person.

*Done when:* cast cards show photographs, and a person with no TMDb
`profile_path` renders without a broken image.

**Stage 3 — Browsable people.** `GET /Persons` (paged query result),
`GET /Persons/{name}` (single person — Jellyfin addresses this endpoint by
**name**, not id), and a `personIds` filter on `/Items`.

*Done when:* clicking a cast member opens their page listing every title of
theirs in the library.

**Stage 4 — TV credits.** Series cast from the series-level TMDb credits;
episode-level guest stars and directors/writers on episodes. Requires extending
`Metadata.Worker`, which currently matches `%Item{type: :movie}` only.

*Done when:* a series page lists its regular cast and an episode lists its
guest stars.

**Stage 4 cannot be verified against the current production data** — there is
no TV library and no TV item. It ships with test coverage only, and should be
confirmed by hand once a TV library exists. This is a real limitation, not a
formality: every TV-related assumption here is unexercised.

## 8. Testing

| Level | Approach |
|-------|----------|
| Credits mapping | Pure function over a recorded TMDb payload; assert cast/crew split, job→kind mapping, dropped jobs |
| Dedup | The same TMDb person across two movies yields one `people` row and two `item_people` rows |
| Re-ingest | Re-running metadata replaces rows rather than duplicating them |
| DTO | `People[]` present with all four fields non-null; absent unless `Fields=People` |
| Images | Person with and without `profile_path`; `/Items/{personId}/Images/Primary` resolves |
| `/Persons` | Paging, name lookup, `personIds` filter returns the right items |

Required-field assertions list key names **literally**, never read from the
implementation's own defaults — a test that derives its expectations from the
code under test agrees with a regression instead of catching it.

Fixtures use a recorded TMDb credits payload rather than live API calls, so the
suite stays deterministic and needs no API key.

## 9. Risks

| Risk | Mitigation |
|------|-----------|
| Cast lists bloat item list responses | `People` gated on the `Fields` check alone, unlike `MediaSources` (§5) |
| Crew table explosion | Job allowlist, unknown jobs dropped (§4) |
| Person id collisions across providers | Dedup key is the TMDb id specifically, not a bare name |
| Re-ingest duplicating rows | Wholesale replace inside a transaction (§4) |
| Image ownership ambiguity | DB check constraint: exactly one of `item_id`/`person_id` (§6) |
| Stage 4 shipping unverified | Stated explicitly (§7); confirm by hand when a TV library exists |
| 7,278 movies re-fetching metadata | Credits ride along on the existing details call; no new requests, and `ProviderCache` already fronts it |
